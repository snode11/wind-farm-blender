# 四相机卡顿诊断

观察目标更正：用户于 2026-09-23 明确要求多台相机分段观察同一片叶片。本报告使用的旧四方向 JSON 不符合这一布局目标；以下数据保留为旧输入下的性能诊断，不作为新布局的帧率或覆盖验收。见 [旧布局状态说明](../camera-layout-test-v1/README.md)。

本机 2026-09-22/23，macOS 26.6.2、Apple M5 Pro、Blender 5.2.1 LTS，复用随扩展提供的 MAPPO 回放与 T1-four-cameras-v1.json。各模式在独立 Blender 进程中串行运行；3 秒预热后约 8 秒计数。没有修改用户正在打开的场景，也没有重跑仿真。

最终 v2 布局的独立复测见 [v2 播放与内存报告](../camera-layout-same-blade-v2/performance/REPORT.md)。下列旧布局对照保留原始条件，不用于计算 v2 的优化提升百分比。

## 结论与边界

1. 原生四路仍卡顿的主要已验证因素是场景动态更新时的阴影绘制。关闭阴影、降低阴影分辨率都明显提速；关闭太阳灯阴影也有明显改善。完整动态更新冻结后约 18 FPS，仅为诊断对照，不能用于真实叶片回放。
2. 原生相机同步约 1 ms/次，关闭后从约 2.19 到 2.28 FPS；关闭额外原窗口也只到约 2.52 FPS。它们不是本次测到的主要瓶颈。四台原生观察相机固定存在，没有每帧新增相机或重复运行四次仿真。
3. 场景有 2363 个可见 Mesh、约 118 万基础顶点，其中 2263 个是景观对象。四视口各自承担材质与阴影绘制成本；本测试没有做底层 GPU profiler，不能精确归因于某个 GPU 内部算法。
4. 草地变为纯绿色来自先前原生视口的 SOLID 着色。当前默认 MATERIAL 并继承原窗口的场景灯光与环境，保留贴图和颜色管理。未把关闭阴影、降低纹理尺寸或工作室环境写成默认值。
5. 上表峰值 RSS 是单个新进程的短测值，不能代表整机统一内存/显存压力，也不能据此排除长时间内存增长。旧离屏四格已被移除；单路精确编辑与按需四相机原图导出仍使用 GPU 离屏绘制，但不参与原生四路刷新。

可继续采用的优化方向：为交互回放提供降低阴影精度的选项，精确检查和原图导出保留原质量。0.5 比例本机约 8 FPS，仍未达到流畅的 30/60 FPS；目前只完成诊断，没有暗中修改默认阴影质量。

复现脚本：measure.py。原始测量：各模式同名 JSON；日志与 scene-inventory.json 同目录。任何新对照请串行运行，避免多个 GPU 进程相互竞争。
