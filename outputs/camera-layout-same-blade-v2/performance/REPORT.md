# 最终 v2 布局：播放卡顿与内存实测

2026-09-23，本机安装版 Blender 5.2.1 LTS，macOS 26.6.2 arm64，Apple M5 Pro。结论：**旧四幅离屏预览未运行，原生四路仍明显掉帧，而且原窗口一起变慢。** 原画质四路约每秒 7.09 次有效画面更新；阴影分辨率减半约 10.93 次，仍未达到流畅播放。默认画质未修改。

## 最终参数与测量

输入为 [T1-same-blade-four-cameras-v2.json](../T1-same-blade-four-cameras-v2.json)，SHA-256：`ee033ac02581fba40c7e0acf828a58dcde60b10910bc911c3f086a7cf9fa1f13`。每组在独立 Blender 进程串行运行，导入最终布局，加载和开始播放后分别等待 3 秒，回到第 1 帧开始约 62 秒测量。使用已有 MAPPO 数据，没有重跑仿真或保存用户场景。实际安装路径记录于各 JSON 的 `environment.addon_path`，没有用仓库源码冒充安装版运行。

当前片段为第 1–3601 帧、场景标称 60 FPS，对应 117–177 s 的 60 秒仿真数据。所有下表有效测试均实际经过一次时间轴回绕并继续更新；不能把时间轴的60 FPS当作画面真正更新频率，也不把其他“66秒demo”自动当作同一数据片段。

下表“更新/秒”计算为 POST_PIXEL 回调中，场景整数帧号相对上次发生变化的次数／实际墙钟秒数；不计连续相同帧，不测显示器物理呈现、GPU完成时刻或子帧。各 JSON 中的 `fps` 沿用脚本字段名。RSS 为 `ps` 的单进程驻留内存，GiB 单位；全进程峰值包含启动、预热和测量，不等于纯测量窗口峰值或完整GPU／统一内存压力。

四路原画质中，原窗口和 C1–C4 各自均为443次更新。**四路窗口虽共享场景和时间轴，四个视口仍各自承担绘制成本，额外原窗口也在重绘。** 这些值反映该窗口组合的整体负载，不能称仅四路的孤立成本。

所有有效测试的每个相邻采样区间里，各路绘制计数都继续增加；复核记录见 [validation.json](validation.json)。单路和四路都保留材质、贴图、场景灯光与环境。原窗口逻辑尺寸约1728×957–960；单路窗口820×430，四路窗口820×432。Blender 报告的四路各视口物理区域约812–813×424–425，原窗口3D区约2832×1678–1684；高DPI逻辑窗口尺寸与区域像素不能直接相加比较。不同屏幕、窗口大小、系统负载和热状态可能改变结果，本表为各模式一次有效运行，不作稳定性能承诺。

## 卡顿原因与内存

- 被包装计数的旧入口 `custom_camera_preview.render_group` 在各有效运行中调用次数为0，约0.5秒采样均未见旧预览渲染器实例。该证据指向已移除的自定义离屏预览路径，不宣称Blender内部所有GPU离屏操作均为0。
- 观察相机代理数固定：单路1个，四路4个；没有每帧累加，退出后均为0。共享正式回放数据，并未复制四份仿真。
- 此布局的阴影分辨率比例0.5对照提高了画面更新频率；结合[此前旧布局的多项对照](../../camera-lag-diagnosis/REPORT.md)，动态场景的阴影绘制是主要已验证开销之一。没有底层GPU profiler，不能归因于某个内部算法，也不能把这一选项等同于完整性能修复。实验只在独立进程设置，没有写入JSON、默认安装配置或用户场景，阴影细节质量也未作完整验收。
- 原画质四路 RSS 0.544→0.596 GiB，约增加53 MiB。多数中间样本在0.529–0.55 GiB附近波动，结束时升高；不能描述为“内存下降”或“零增长”。进程峰值约1.092 GiB，关闭窗口两秒后约0.634 GiB。短测与代理对象回收不足以排除长时泄漏，关闭后RSS也不会必然立即回落。
- 原画质四路约0.5秒周期定时回调的迟到P95约183ms、最大约286ms。这是调度迟到，包含主线程忙碌等影响，不是鼠标输入到屏幕显示的实测延迟。

## 异常记录与验证范围

首次62秒单路测量在结束清理时发生 `TypeError: Window not found`，错误发生在进入 `temp_override`，尚未执行暂停操作；当时窗口不在可用列表，原因未确认。没有归因为用户关闭或Python对象重包装，也没有修改生产代码冒充修复。错误及日志保留于 [single-attempt-1](single-attempt-1/single-error.txt)。基准补充存活窗口指针与关闭调用记录后，单路重新运行约62.55秒，通过完整播放、一次回绕、持续更新和退出清理；原异常仍是未定位的单次现象。

第一次阴影减半测试在约30.7秒后停在frame1852、各路计数342。原脚本当时只要求总计数非零，虽然输出PASS，但逐样本复核发现后半程未播放，因此**5.48/s这个混入静止时间的平均值无效**。原始文件保存在 [shadow-half-attempt-1](shadow-half-attempt-1/VALIDITY.md)，不作为表内数据。已增加超过2秒计数不变的断言并重新运行，表内是持续更新且回绕的有效复测。

下表有效运行均在退出时打印同一条 `Not freed memory blocks: 525, total unfreed memory 0.038147 MB`，Down基线也存在。此日志不能直接归因于新相机，但不得据此宣称全进程零残留或零泄漏。日志分别位于上级目录的 `benchmark-down.log`、`benchmark-single.log`、`benchmark-quad.log`、`benchmark-quad_shadow_half.log`。

本轮没有进行长时间循环、频繁开关窗口压力、真人输入延迟、显存耗尽或Windows/Linux验收。当前可交付的是可导入的同一叶片分段试用布局、旧离屏路径移除及上述真实播放证据；**四路仍不流畅，长期内存稳定性尚未证明。**

## 复现

从仓库根目录运行，每次只启动一个进程。原始记录默认写入本目录同名JSON；需要保留历史时先另存本目录。MODE 可选 down、single、quad、quad_shadow_half；后者只作阴影质量对照。

```sh
WFRL_ADDON_PATH='/Users/eason/Library/Application Support/Blender/5.2/extensions/user_default' \
LAYOUT_BENCH_MODE=quad LAYOUT_BENCH_SECONDS=62 \
/Applications/Blender.app/Contents/MacOS/Blender --factory-startup \
  --python outputs/camera-layout-same-blade-v2/benchmark.py
```

[测量脚本](../benchmark.py)只在独立实例构造场景、导入布局并测试，不保存用户`.blend`。默认画质保持不变；正式原图导出仍由显式采集操作执行。
